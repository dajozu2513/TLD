Procesos y sesiones

Ver fórmula del Indicador de Procesos (IP)
1. Utilización = máx(procesos actuales ÷ límite, sesiones actuales ÷ límite) × 100 2. Score según la utilización: < 50% → 95 + (50 − util) × 0.1 50–70% → 80 + (70 − util) × 0.75 70–85% → 65 + (85 − util) × 1.0 85–95% → 40 + (95 − util) × 2.5 ≥ 95% → máx(5, 40 − (util − 95) × 4) 3. Penalizaciones adicionales: − mín(25, sesiones bloqueadas × 6) − mín(12, long ops × 3) IP = clamp(score, 0, 100) *clamp asegura que el resultado nunca sea menor a 0 ni mayor a 100.

Ver umbrales del Indicador de Procesos (IP)
Umbrales de utilización (procesos/sesiones vs. su límite): < 50% — margen amplio, sin riesgo 50–70% — uso saludable, ya vale la pena vigilar tendencia 70–85% — advertencia temprana 85–95% — riesgo real ante un pico de carga ≥ 95% — crítico: al 100% Oracle rechaza conexiones nuevas (ORA-00020); se deja ese margen de reacción Penalizaciones aparte de la utilización (síntomas activos, no capacidad): Sesión bloqueada: −6 pts c/u (tope −25). Un solo bloqueo ya es un problema activo aunque la base esté poco cargada; el tope evita que muchos bloqueos aplasten el resto de la fórmula. Long op en curso: −3 pts c/u (tope −12). Pesa la mitad porque no siempre es un problema — puede ser mantenimiento normal (ej. crear un índice). Justificación de umbrales Se escogieron umbrales de tipo semáforo (70/85/95%), un patrón estándar en monitoreo de sistemas, dejando la zona crítica justo antes del 100% — el punto donde Oracle empieza a rechazar conexiones — para darle margen de reacción al DBA. Justificación de penalización Una sesión bloqueada es un problema cualitativamente distinto a "muchas conexiones" — puedes tener solo un 20% de utilización de procesos (nada saturado) y aun así tener un bloqueo grave que está paralizando una transacción crítica. Si el IP solo mirara utilización, este escenario se vería "saludable" cuando en realidad hay un problema activo. Por eso se resta aparte, independientemente de qué tan ocupada esté la base. Se separó la penalización por síntomas activos (bloqueos, long ops) de la utilización general, porque un sistema puede tener capacidad de sobra y aun así tener un problema puntual grave. Los bloqueos pesan más que los long ops porque un bloqueo siempre indica contención real, mientras que un long op puede ser una operación de mantenimiento normal.

    Memoria (SGA / PGA)

    Ver fórmula del Indicador de Memoria (IM)
    IM parte de un puntaje base de 92 y resta una penalización por cada señal de presión: Uso de SGA = (Tamaño SGA − Memoria libre SGA) ÷ Tamaño SGA × 100 > 95% → −18 > 90% → −10 > 85% → −5 Uso de Shared Pool > 95% → −8 > 90% → −4 Uso de Buffer Cache (Hit Ratio: alto es bueno, aquí penaliza cuando es bajo) < 80% → −15 < 90% → −8 < 95% → −3 Uso de PGA = PGA utilizada ÷ PGA máxima × 100 > 95% → −15 > 85% → −8 > 75% → −3 Over-allocation (conteo de eventos, no %) > 20 → −20 > 5 → −12 > 0 → −5 Cache hit de PGA < 70% → −15 < 85% → −8 < 92% → −3 IM = clamp(92 − penalizaciones, 0, 100) *clamp asegura que el resultado nunca sea menor a 0 ni mayor a 100.

    Ver umbrales del Indicador de Memoria (IM)

    Por qué esta fórmula y no una curva única como el IP: El IP mide un solo eje de riesgo (qué tan cerca del límite de procesos/sesiones), por eso usa una curva continua. El IM combina seis señales independientes de subsistemas de memoria distintos (SGA, Shared Pool, Buffer Cache, PGA, Over-allocation, PGA Cache Hit) que pueden fallar por separado — un problema en el Shared Pool no tiene relación técnica con un problema de Buffer Cache. Por eso se parte de un puntaje base de 92 y se le restan penalizaciones independientes por cada una, en vez de forzarlas a una sola fórmula continua.

    Por qué no hay un techo conjunto (a diferencia del IP): en el IP, un MIN(...) evitaba que un solo síntoma (bloqueos) aplastara todo el puntaje. En el IM, cada variable ya penaliza con moderación por separado; si las seis fallaran a la vez, el puntaje sí debe caer fuerte, porque significaría que toda la gestión de memoria está comprometida a la vez, no solo un aspecto puntual.

    Umbrales y peso exacto de cada escalón:

    VariableEscalón 1Escalón 2Escalón 3
    Uso SGA>85% → −5>90% → −10>95% → −18
    Shared Pool>90% → −4>95% → −8—
    Buffer Cache Hit<95% → −3<90% → −8<80% → −15
    Uso PGA>75% → −3>85% → −8>95% → −15
    Over-allocation>0 → −5>5 → −12>20 → −20
    PGA Cache Hit<92% → −3<85% → −8<70% → −15

    Por qué cada variable pesa distinto:

    Uso SGA (hasta −18, la 2ª más alta): memoria compartida — si se agota, afecta a toda la instancia por igual, no solo a una sesión.

    Shared Pool (hasta −8, la más baja): el peor caso es re-parseo de SQL (más lento, pero la base sigue respondiendo) — impacto real pero acotado.

    Buffer Cache Hit (hasta −15): alto = bueno; un hit ratio bajo implica I/O físico frecuente, órdenes de magnitud más lento que memoria — cambio cualitativo de rendimiento, no gradual.

    Uso PGA (hasta −15): memoria privada por proceso, más volátil que la SGA (puede dispararse de golpe con una sola sesión pesada) — impacto algo más acotado que la SGA porque no golpea a toda la instancia por igual.

    Over-allocation (hasta −20, la más alta de todas): a diferencia de las demás, no es una proyección de riesgo — confirma que Oracle ya excedió PGA_AGGREGATE_TARGET al menos una vez. Por eso penaliza desde el primer evento (−5 con solo 1 caso), sin zona neutral.

    PGA Cache Hit (hasta −15): alto = bueno; mismo peso que Buffer Cache Hit, pero con umbrales más bajos (92/85/70% en vez de 95/90/80%) porque el rendimiento natural de la PGA en estas operaciones es menor.
